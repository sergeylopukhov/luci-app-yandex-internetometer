# План реализации и выпуска v1.0.0

## 1. Цель

Исправить заниженную исходящую скорость при запуске теста непосредственно на OpenWrt-роутере. Сейчас upload выполняют HTTPS-процессы `curl`, поэтому результат может отражать предел CPU/TLS роутера, а не пропускную способность WAN.

В версии `v1.0.0` список probe-серверов по-прежнему нужно получать через защищённый API Яндекса, а тестовые download/upload-потоки в основном режиме передавать к тем же Yandex CDN по HTTP. Это исключит TLS-шифрование тестового трафика, не добавит Wi-Fi или устройство пользователя в измеряемый тракт и сохранит схему «роутер → Yandex CDN».

## 2. Подтверждённые исходные условия

- `https://yandex.ru/internet/api/v0/get-probes` возвращает HTTPS-адреса CDN для latency, download и upload.
- Актуальные Yandex CDN принимают download и upload по HTTP без перенаправления на HTTPS и отвечают `200 OK`.
- Через upload передаются только синтетические нулевые данные; конфиденциальных пользовательских данных в потоке нет.
- Текущая версия проекта — `0.0.1-r22`, последний Git-тег и GitHub Release — `v0.0.1`.
- GitHub Pages публикуется из `main:/docs`.
- В GitHub настроен секрет `YANDEX_INTERNETOMETER_APK_PRIVATE_KEY`.

Перед реализацией нужно повторно проверить поведение живых endpoint: оно внешнее и может измениться.

## 3. Требуемая архитектура

### 3.1. Режим передачи

Добавить настройку `transfer_protocol` со значениями:

- `auto` — значение по умолчанию: проверить HTTP перед тестом, использовать его при успешной проверке, иначе перейти на HTTPS;
- `http` — использовать HTTP; при недоступности вернуть понятную ошибку без скрытого fallback;
- `https` — совместимый режим для диагностики и отката.

API `get-probes` и получение публичного IP всегда оставлять на HTTPS. На HTTP переводить только синтетические download/upload-запросы.

Перед заменой схемы URL проверить, что исходный адрес:

- использует `https://`;
- принадлежит хосту с суффиксом `.cdn.yandex.net`;
- содержит ожидаемый download- или upload-путь.

Нельзя понижать протокол для произвольного хоста из изменённого ответа API.

### 3.2. Проверка HTTP и fallback

До начала учитываемого интервала:

1. Проверить один HTTP download URL коротким запросом без автоматического перехода по redirect.
2. Отправить на один HTTP upload URL небольшой тестовый payload, также вне учитываемого интервала.
3. Считать HTTP доступным только при ответах `2xx`.
4. В режиме `auto` при любой ошибке использовать исходные HTTPS URL.
5. В режиме `http` при ошибке завершить тест с чистым JSON-сообщением.

В результирующий и промежуточный JSON добавить фактически использованный `transfer_protocol` и признак fallback. Показать транспорт в деталях LuCI. При HTTPS-fallback вывести короткое предупреждение, что результат может быть ограничен CPU/TLS роутера.

### 3.3. Исходящий тест

Переработать `measure_upload()`:

- создавать payload как sparse-файл через `truncate`, а при его отсутствии — через совместимый `dd ... count=0 seek=...`;
- проверить apparent size файла, не записывать 30,72 МБ нулей в tmpfs;
- сохранять отдельный файл счётчиков на каждый worker вместо конкурентной записи всех процессов в один файл;
- распределять worker по probe URL циклически, а не отправлять все лишние потоки на первый CDN;
- запускать worker от общего момента старта;
- измерять время монотонно по `/proc/uptime`, а не целыми секундами `date +%s`;
- считать итог по фактически переданным байтам и фактической длительности учитываемого интервала;
- ограничить отдельный HTTP POST коротким интервалом, чтобы `size_upload` обновлялся регулярно и Stop срабатывал быстро;
- не учитывать короткий предварительный разогрев;
- отслеживать PID worker и текущих `curl`, чтобы `stop` и trap завершали всё дерево без оставшихся upload-процессов.

Не возвращать прежний эксперимент с длинным списком URL и одним `--max-time`: у `curl` этот лимит применяется к каждой передаче отдельно, поэтому такой worker способен работать намного дольше общего теста. Если реализуется повторное использование соединения, оно должно иметь отдельный общий watchdog и гарантированное завершение.

### 3.4. Автоматический выбор потоков

`upload_streams=auto` должен действительно выбирать число потоков:

- учитывать количество уникальных upload probe;
- учитывать число доступных CPU;
- при низком `MemAvailable` ограничивать upload двумя worker;
- в обычном случае использовать до трёх-четырёх worker;
- сохранять явное пользовательское значение без самовольной замены.

Удалить миграционную логику, которая превращает старое значение `streams=3` в `8`. Новая установка должна получать безопасные значения по умолчанию, а обновление — сохранять настройки пользователя.

### 3.5. Плавность показаний

Backend должен обновлять сырые накопительные данные примерно раз в секунду. Увеличивать частоту запуска `jq`, `awk` и RPC на слабом роутере не нужно.

В LuCI:

- сглаживать только промежуточное визуальное значение с помощью EMA;
- не сглаживать и не изменять финальный результат;
- продолжить анимацию между обновлениями без пересоздания DOM;
- не показывать ноль до первого достоверного sample;
- одинаково обновить оба поставляемых файла представления и проверить их идентичность.

### 3.6. Уведомление о новой версии

В LuCI обязательно показывать, что для приложения доступна новая версия. Проверка обновлений не должна зависеть от GitHub API, требовать токен или выполняться во время каждого status poll.

Реализовать следующую схему:

1. Хранить установленную версию в поставляемом пакетом локальном файле или другом едином источнике, не дублировать её вручную в нескольких runtime-скриптах.
2. Публиковать через GitHub Pages статический `version.json` с полями `version`, `package_version`, `tag`, `release_url`, `install_url` и `published_at`.
3. Получать `version.json` только по фиксированному HTTPS-адресу с короткими connect/max timeout.
4. Кешировать результат в `/tmp` не менее чем на 6–12 часов. Автоматическая проверка выполняется один раз при открытии страницы, а не при каждом обновлении скорости.
5. Сравнивать версии как числовые компоненты SemVer, а не как строки.
6. При новой версии показать заметный, но неблокирующий блок:
   - заголовок: «Доступна версия 1.0.0»;
   - подпись: «Установлена версия 0.0.1»;
   - основное действие: «Обновить» или, если встроенное обновление недоступно, «Открыть выпуск»;
   - дополнительное действие: «Проверить обновление».
7. При актуальной версии показывать номер установленной версии только в деталях приложения.
8. Ошибка автоматической проверки не должна мешать тесту и не должна создавать постоянное предупреждение. После ручной проверки допустимо сообщение: «Не удалось проверить обновление. Проверьте подключение и попробуйте снова».

Минимальный обязательный результат для `v1.0.0` — уведомление, ссылка на GitHub Release и доступная команда обновления. Проверка должна обнаруживать будущие версии без выпуска нового кода самого уведомления.

Желательный результат — обновление непосредственно из LuCI:

- для `apk` использовать настроенный подписанный репозиторий и фиксированную backend-команду `apk update` + `apk add --upgrade luci-app-yandex-internetometer`;
- запускать обновление асинхронно, показывать этапы и после завершения предлагать перезагрузить страницу;
- перед запуском показывать подтверждение «Обновить до версии X?» с кнопками «Обновить» и «Отмена»;
- не принимать от браузера произвольную команду, URL или имя пакета;
- добавить отдельный wrapper и минимальное ACL-разрешение только для фиксированных операций проверки/обновления;
- для `opkg` или неподдерживаемой конфигурации показывать выпуск и готовую команду установки вместо ненадёжного автоматического обновления.

Если безопасное встроенное обновление нельзя надёжно завершить в рамках `v1.0.0`, оно не блокирует релиз. Уведомление о новой версии блокирует релиз и должно работать обязательно.

### 3.7. Универсальный SH-установщик

Переработать существующий `docs/install.sh` в единый публичный установщик. Второй конкурирующий скрипт создавать не нужно: одна команда должна подходить для первичной установки и последующих обновлений.

Основная команда:

```sh
curl -fsSL https://sergeylopukhov.github.io/luci-app-yandex-internetometer/install.sh | sh
```

Запасной вариант для роутеров без `curl`:

```sh
wget -qO- https://sergeylopukhov.github.io/luci-app-yandex-internetometer/install.sh | sh
```

Установщик должен:

1. Работать в BusyBox-совместимом `/bin/sh`, без Bash, Python и Node.js.
2. Проверять запуск от `root`, наличие OpenWrt и доступность HTTPS-загрузчика.
3. Определять пакетный менеджер:
   - если доступен `apk`, определять архитектуру через `apk --print-arch`, подключать подписанный репозиторий нужной архитектуры и устанавливать/обновлять APK;
   - если `apk` отсутствует, но есть `opkg`, скачивать подходящий IPK из актуального GitHub Release и устанавливать/обновлять его;
   - если обнаружены оба менеджера, использовать штатный для текущей версии OpenWrt, а при неоднозначности явно сообщить выбранный вариант;
   - если не найден ни один поддерживаемый менеджер, завершаться с конкретной инструкцией, что проверить.
4. Получать актуальную стабильную версию из фиксированного HTTPS `version.json`, валидировать формат версии и строить URL только для доверенных доменов проекта.
5. Определять, установлен ли пакет, и выбирать действие: установка, обновление, переустановка той же версии или отказ от случайного downgrade.
6. Сохранять пользовательский UCI-конфиг при обновлении. Перед первой изменяющей операцией делать не больше одной датированной резервной копии `/etc/config/yandex-internetometer`, если файл существует.
7. Создавать временный каталог через `mktemp -d`, удалять только его через trap и не очищать общие кеши пакетного менеджера широкими glob-командами.
8. Для APK полагаться на подпись существующего репозитория и не заменять доверенный ключ случайно сгенерированным.
9. Для IPK скачивать опубликованный `SHA256SUMS`, проверять checksum до установки и завершаться ошибкой при несовпадении.
10. Не использовать `eval`, не выполнять команды или URL из непроверенного ответа и не запускать второй удалённый shell-скрипт.
11. После установки проверить фактическую версию пакета, наличие исполняемого backend, валидный ответ команды `status`, очистить только кеш LuCI-приложения и перезагрузить `rpcd`.
12. В финале показать установленную версию и путь в интерфейсе: `LuCI → Статус → Интернетометр`.

Вопросы задавать только там, где безопасное решение нельзя выбрать автоматически: неподдержанная версия OpenWrt, принудительный downgrade, переустановка той же версии или конфликтующая конфигурация репозитория.

Так как команда использует `curl | sh`, вопросы нельзя читать из обычного stdin. Интерактивный режим должен читать ответы из `/dev/tty`. Если TTY недоступен, установщик обязан выбрать безопасный вариант, завершиться без опасного изменения или предложить повторный запуск с явным флагом.

Предусмотреть аргументы:

- `--yes` — принять безопасные значения по умолчанию без вопросов;
- `--force` — разрешить переустановку или явно запрошенный downgrade после дополнительных проверок;
- `--version` — показать версию установщика;
- `--help` — показать команды и примеры.

Для передачи аргументов через pipe документировать форму:

```sh
curl -fsSL https://sergeylopukhov.github.io/luci-app-yandex-internetometer/install.sh | sh -s -- --yes
```

Тексты установщика должны быть краткими и объяснять действие: «Найден apk», «Обновляем список пакетов», «Устанавливаем версию 1.0.0», «Установлена версия 1.0.0». Ошибка должна сообщать причину и следующий шаг. По умолчанию использовать русский язык; при нерусской локали или `INSTALLER_LANG=en` показывать английские сообщения.

## 4. Совместимость и безопасность

- Сохранить CLI-команды `run`, `start`, `status`, `stop` и существующие JSON-поля.
- Новые JSON-поля добавлять без удаления старых.
- Не добавлять Python, Node.js, отдельный бинарный helper или новый сервер в runtime-зависимости пакета.
- Не отправлять пользовательские данные по HTTP: только нулевой upload-payload и тестовый download.
- В README явно объяснить компромисс: HTTP убирает нагрузку TLS, но промежуточный узел теоретически может повлиять на тестовые данные или результат.
- Оставить принудительный режим HTTPS как быстрый rollback без переустановки пакета.

## 5. Проверки реализации

### 5.1. Автоматические и локальные проверки

Обязательно выполнить:

1. `sh -n` для всех shell-скриптов.
2. `shellcheck`, если он доступен.
3. `node --check` для LuCI JavaScript, если Node.js доступен локально.
4. `git diff --check`.
5. Проверку идентичности двух файлов LuCI-представления.
6. Тест выбора `auto`, принудительных `http`/`https` и HTTP-fallback с подменённым `curl`.
7. Тест round-robin при трёх URL и 1, 2, 3, 4, 8 worker.
8. Тест расчёта скорости по дробной фактической длительности.
9. Тест, что sparse-payload имеет нужный apparent size и не занимает сопоставимый объём блоков/RAM.
10. Тест Stop: после завершения не остаётся дочерних `curl`.
11. Проверку валидного JSON для успеха, fallback и ошибок.
12. Тест сравнения версий: равные версии, новая patch/minor/major, а также защита от лексикографической ошибки `1.10.0` против `1.9.0`.
13. Тест кеша обновлений, таймаутов и недоступного `version.json`: проверка обновлений не должна ломать страницу или запуск теста.
14. Если добавлено встроенное обновление — тест запрета произвольных URL/команд и корректных состояний «проверка», «обновление», «готово», «ошибка».
15. Тест установщика с подменёнными `apk` и `opkg`: новая установка, обновление, актуальная версия, отказ от downgrade и ошибка пакетного менеджера.
16. Тест определения apk-архитектуры, выбора правильного `packages.adb` и сохранения существующего UCI-конфига.
17. Тест IPK-ветки: успешная проверка `SHA256SUMS`, несовпадение checksum и недоступный GitHub Release.
18. Тест запуска через pipe: чтение вопроса из `/dev/tty`, отсутствие TTY, `--yes`, `--force`, `--help` и неизвестный аргумент.
19. Тест уборки временного каталога и отсутствия изменений общих кешей или посторонних файлов.
20. Проверку русских и английских сообщений установщика.
21. Проверку README: команды совпадают с рабочим установщиком, относительные ссылки и изображения открываются, badges актуальны, старые версии и URL отсутствуют.

### 5.2. Живой smoke-тест endpoint

Перед релизом повторно проверить:

- получение probe по HTTPS;
- HTTP download с ответом `2xx` без redirect;
- небольшой HTTP upload с ответом `2xx`;
- HTTPS-fallback на искусственно недоступном HTTP URL.

Не запускать с рабочей машины полный гигабитный тест без необходимости.

### 5.3. Проверка на роутере

Если доступ к тестовому OpenWrt-роутеру существует, установить кандидат и сделать не менее трёх замеров:

- HTTP/auto на роутере;
- HTTPS на роутере;
- Яндекс Интернетометр на подключённом по Ethernet компьютере как внешний ориентир.

Зафиксировать медиану upload, загрузку CPU, `MemAvailable`, фактически выбранные потоки и транспорт. Проверить LuCI, CLI JSON, Stop и отсутствие оставшихся процессов.

Если доступа к роутеру нет, не выдавать аппаратную проверку за выполненную. Релиз разрешено продолжить после автоматических тестов и живого endpoint smoke-теста, но отсутствие проверки на реальном роутере нужно явно указать в итоговом отчёте.

### 6.1. Пользовательский README

Полностью переписать `README.md` для обычного владельца OpenWrt-роутера. Читатель должен за минуту понять назначение приложения, установить его одной командой и найти страницу в LuCI. Подробности реализации не должны мешать этому сценарию.

Требования к содержанию:

1. Начать с названия, одного короткого описания и явной пометки, что проект неофициальный и не связан с Яндексом.
2. На первом экране показать:
   - аккуратный скриншот актуального интерфейса `v1.0.0`;
   - одну основную команду установки;

До создания тега:

7. Публиковать `version.json` только после успешного создания GitHub Release и загрузки его assets, чтобы LuCI не предлагал ещё недоступное обновление.
8. Генерировать и публиковать `SHA256SUMS` для release assets; универсальный установщик должен проверять IPK по этому файлу.

## 9. Критерии готовности

Версия `v1.0.0` готова, когда одновременно выполнено следующее:

- тест по умолчанию остаётся router-side и не зависит от Wi-Fi/браузера пользователя;
- список probe и служебные данные идут по HTTPS;
- синтетический throughput в режиме `auto` использует HTTP и корректно откатывается на HTTPS;
- JSON и LuCI показывают фактический транспорт;
- upload равномерно использует CDN и не создаёт полноценный 30,72-МБ файл в RAM;
- промежуточная скорость обновляется без длинного нуля и резкого финального скачка;
- итог рассчитан по фактическому времени, а Stop не оставляет процессы;
- LuCI обнаруживает более новую версию через кешируемый HTTPS-запрос, показывает уведомление и ведёт на реальный опубликованный выпуск;
- сбой проверки обновлений не влияет на замер скорости;
- одна публичная SH-команда сама выбирает apk или opkg, устанавливает либо обновляет пакет, проверяет целостность и сохраняет конфигурацию;
- необходимые вопросы работают при `curl | sh` через `/dev/tty`, а неинтерактивный режим не принимает опасные решения молча;
- README коротко объясняет пользу приложения, показывает установку на первом экране, аккуратно оформлен и проверен сначала через `ru-text`, затем через `metaflora-humanizer`;
- старые команды и конфигурация совместимы;
- проверки проходят;
- `main`, тег `v1.0.0`, GitHub Release, release assets и GitHub Pages подтверждены на опубликованных URL.
